You are the implementation lead for a full V2 rebuild of the Trend Detective user experience. The app is an entry for the NASA Space Apps Challenge. The backend has been built and reviewed, but must pass the Phase 0 repair gate below before optional live features are wired into the public UI.

The desired visual direction is:

NON-NEGOTIABLE SCIENCE AND SAFETY RULES

1. Keep the existing audited statistics. The frontend must display backend values; it must never recalculate or alter p-values, slopes, confidence intervals, evidence grades or forecast eligibility.
2. NASA POWER provides historical/reanalysis trend data. Meteomatics provides current and 1–72 hour operational weather. The app’s internal monthly model provides 1–3 month statistical forecasts. These three sources must never be averaged, merged into one timeline scale without a boundary, or labelled as each other.
3. News is context, not scientific evidence. Its green/amber/red border is a transparent editorial attention label, not an official emergency warning.
4. “Why might this be happening?” is manual/opt-in only. It gives possible, cited explanations after a valid trend exists; it never proves a cause.
5. Profiles, saved locations and preferences stay in browser localStorage only. This is a local demo profile, not a secure account system. No password, profile database, cookie authentication or cloud user record.
6. Never expose OPENAI_API_KEY, Meteomatics credentials, a news-provider key, TD_CASE_SECRET or any other secret to browser code, logs, screenshots, Git or prompts.
7. Preserve keyboard globe controls, responsive layout, focus visibility and prefers-reduced-motion. Motion must pause while the user drags/interacts with the globe and reduce to non-animated state changes when reduced motion is enabled.

FABLE DESIGN SPECIFICATION
====================================================================

Fable should prepare the visual system before implementation. The design output must cover:

1. Page structure

   TOP BAR
   - Brand at left.
   - Compact Account/Profile button at top-right.
   - Minimal controls only; avoid a crowded navigation strip.

   MAIN DASHBOARD
   - Left: personalised dashboard.
   - Centre/right: dominant interactive globe.
   - Bottom of globe: timeline and playback controls.
   - Main content uses the user’s selected data types and saved places first.

   EXPLORE PAGE
   - Holds the “neeky”/advanced tools: Sweep, Scan, Duel, World, Vitals, Ledger, Events, statistical detail and learning resources.
   - Must be reachable in one clear click and support browser back/forward/history state.

2. Dark mission-control design tokens

   - Near-black/navy background; deep ocean blue globe; restrained atmospheric halo.
   - Data colours must be semantically consistent and colour-blind distinguishable:
       temperature/positive anomaly: warm amber to red;
       cooling/negative anomaly: cyan to blue;
       rainfall/water: blue/teal;
       cloud: pale slate/white;
       missing data: patterned neutral, never a data colour;
       news severity: green, amber, red border only;
       forecast: a visually distinct dashed/hatched treatment.
   - Use CSS variables so themes remain consistent across SVG/canvas/HTML.
   - Maintain strong readable text contrast and avoid red/green as the only severity cue.

3. Animation rules

   - Globe idle rotation: slow, subtle; pause on focus, drag, keyboard input, hidden tab and reduced motion.
   - Timeline: scrub by month; play/pause; speed choices; accessible keyboard range input; no forced autoplay.
   - Data layers cross-fade or interpolate only between genuine adjacent frames. Missing cells are a pattern or transparent gap, never smoothed.
   - Forecast begins at a clear observed/forecast divider. It uses a distinct label, border and legend.
   - Loading state: show a radar/data-scan feeling without claiming data have arrived.

4. Responsive wireframes

   - Desktop: dashboard left, globe right/centre, timeline underneath globe.
   - Tablet: dashboard becomes collapsible/drawer; globe remains primary.
   - Mobile: full-width globe then timeline, dashboard as stacked cards/bottom sheet; no tiny controls.

5. Asset rules

   - When a real NASA/public layer is available and its use/licence/performance are documented, use it with an explicit source/attribution label.
   - When it is not available, use a clearly decorative procedural atmosphere/cloud/lighting effect. Never imitate an unavailable live satellite product.
   - No NASA logo and no unlicensed satellite image download.

====================================================================
CLAUDE FRONTEND IMPLEMENTATION REQUIREMENTS
====================================================================

1. Local welcome and profile

- First run: show “Welcome, Trend Detective” rather than a misleading password login.
- Ask in five short steps: display name or Demo Explorer; up to five saved locations; interests (heat, rain & water, clouds & sunlight, land & plants, wind & atmosphere, ice & oceans); primary goal; detail level.
- Store a versioned `td-profile-v2` value in localStorage. Migrate old V1 preferences, tolerate corrupted/blocked storage and offer reset/export/import.
- Account button opens an edit panel. It must say “Stored on this device for this demo.”
- Load only selected locations and selected data interests in the home dashboard. Do not trigger global survey, news or forecasting on initial load.

2. Main versus Explore navigation

- Main is the dashboard/globe/data experience.
- Explore contains advanced tools. Preserve the current capabilities rather than deleting them.
- Use a clear URL/history-friendly page state, browser back/forward, and accessible tabs or navigation.
- “Flip between pages” should feel immediate but must not trap focus or lose the current selected place/variable.

3. Globe and historical timeline

- Reuse the existing custom canvas globe rather than adding a heavy map package.
- For a selected NASA variable/location, call GET /api/monthly-frames and visualise the local 1x1–3x3 observed grid as a dynamic heatmap/field on Earth.
- The user can scrub backwards through past months, press play/pause and change speed. Every frame shows the month, source, unit and local-grid caveat.
- The heatmap must not imply full-world high-resolution satellite coverage. It is a coarse local NASA POWER/reanalysis analysis grid.
- On a globe-wide world-survey/explore mode, retain the existing sample-site time-lapse and label it as sample sites; do not invent a complete global field.
- Render missing cells as missing. Do not interpolate or colour them like valid data.

Important current capability boundary: the delivered backend does not provide a high-resolution globe-wide monthly raster. It provides a local 1×1–3×3 NASA POWER grid near the selected location and the existing global sample-site survey. Build a compelling local heatmap on the Earth, and use sample-site dots for the global view. Do not paint a smooth full-Earth “temperature map” from sparse points. A future true global raster requires a separately scoped backend/data-source phase and its own provenance/performance design.

4. Three separate data modes on the globe/timeline

   A. Observed history
   - NASA POWER monthly local grid from /api/monthly-frames.
   - Label: Observed/reanalysis, NASA POWER.

   B. Internal climate forecast
   - /api/monthly-forecast for T2M, PRECTOTCORR and CLOUD_AMT only.
   - Only render frames when `eligible === true`.
   - When withheld, leave the historical timeline usable and show the backend reason.
   - Label exactly as forecast/not observed; surface backtest metrics in a detail drawer.

   C. Meteomatics live weather
   - /api/live-weather is point-based hourly operational weather for the next 1–72 hours.
   - Present it as a local weather card and optional point/radial layer near the selected location, not a full global heatmap unless a separately documented gridded Meteomatics endpoint is implemented later.
   - Show Meteomatics source, valid/fetch time, stale state and distinct `not NASA trend data` label.

5. News markers

- Fetch news lazily only for saved locations plus the selected interest/data category. Do not run a global news feed.
- Markers appear at approximate saved-location coordinates and rotate with the globe.
- Each closed marker/card shows: thin green/amber/red border, headline, publisher, date and one-line overview.
- On click or keyboard activation, expand in place or open a focus-managed panel with the full available summary, source link, location precision, stale state and the fixed “news context, not scientific evidence” label.
- `publisher_verified: false` stories must say “Unverified news context” and be visually less prominent. Do not claim an official severity level.
- Handle loading, no stories, stale stories, provider error and slow first response without a blank panel.

6. Evidence and manual Why

- Use evidence_trace.verdict to render the four evidence states: Strong evidence of a trend; Some evidence — investigate carefully; No clear evidence yet; Not enough data to tell.
- Lead with direction, rate, period, source and uncertainty. Do not lead with raw p-values.
- Add an expandable “How did we test this?” section that explains each backend evidence_trace step in simple language, then exposes actual values/method names for technical users. It must not pretend calculation occurs in the browser.
- Only after a valid analysis is complete, show a button: “Why might this be happening?”
- Call POST /api/explanations with only the documented signed case and optional short question. On HTTP 422 from a stale case signature, refetch the trend then retry once.
- Render summary, possible drivers, limitations and clickable citations. Always display: “These are possible explanations, not proof that one cause created this local trend.”
- Support `ok`, `fallback`, `no_key`, `rate_limited` and `no_evidence` states intentionally.

7. Failure, performance and accessibility

- Use AbortController/cancellation for stale selection requests and cache only non-sensitive public responses in the browser.
- Budget NASA grid requests; do not request a 3x3 grid and forecast for every saved location in the background.
- Ensure every interactive canvas function has keyboard/ARIA alternate controls and plain-text state information.
- Test desktop, tablet and mobile; normal, slow and failed API states; no keys; no Meteomatics account; stale weather/news; withheld forecast; missing localStorage; and reduced motion.
